# SoloWeave 项目选型与推荐重设计

日期：2026-10-10。状态：本地已实施，真实客户端行为待复测。适用范围：Skills 优先版本的 `project-setup`，不改变已发布 Go CLI 的预设目录。

## 问题与目标

用户的 Codex 试用中，Agent 把“待办应用”直接理解为静态浏览器页面；要求前后端分离后，又只列出三套绑定好的技术组合。当前 `project-setup` 只要求展示“少量可行选项”，没有规定先识别项目类型、按维度展示候选和检查组合兼容性。这偏离了 [v0.2 设计基准](../../design-v0.2.md)中让开发者分别选择技术与架构的方向。

新流程应让 AI **先了解项目需求、识别项目类型，再按适用维度推荐可组合的候选**。项目类型是识别问题的起点，不是技术选型的限制。AI 应根据需求、现有代码和可核对的资料生成候选，不受参考文件所列技术或组合约束。开发者可以逐项选择、接受有依据的推荐或提出自定义方案；AI 检查组合是否成立，关键决定经开发者确认后才生效。普通用户只需在 AI 中描述项目，不依赖 Go CLI。

## 项目范围

第一版覆盖以下项目类型，允许一个项目同时属于多种类型：

| 类型 | 需要识别的特有问题 |
| --- | --- |
| Web 前端、后端 API、全栈 Web | 渲染方式、服务边界、数据持久化、API 与部署。 |
| 移动端 | 目标平台、原生或跨平台、离线与同步、应用分发。 |
| 桌面端 | 目标操作系统、原生或跨平台、本地数据、打包与更新。 |
| CLI／自动化 | 运行环境、跨平台要求、配置与凭据、分发方式。 |
| 数据／AI | 数据来源与敏感性、处理流程、模型运行位置、评估和成本。 |

遇到游戏、嵌入式或其他类型时，先依据需求生成适用维度，不能强套 Web 选型表。类型可以混合，也可以由 AI 提出新类型；表中未列出的类型不应被拒绝或降级。已有项目以实际代码、依赖、运行方式和已批准 ADR 为起点；接入 SoloWeave 不自动触发换栈。

## 交互流程

1. **理解需求**：读取已有项目事实；新项目了解目标用户、核心功能、运行平台、数据与离线需求、部署环境、预算以及团队已有经验。只询问会改变关键推荐的缺失信息；用户已给出的约束不重复问。若“待办应用”这类描述不足以判断是纯前端还是独立后端，先澄清项目形态或并列说明形态差异，不直接落定静态页面。
2. **确定决策维度**：按项目类型选用相关维度。共通维度包括语言与运行时、应用架构、仓库组织、数据存储、测试与交付；再加入各类型专属维度。无关维度不强制填写。例如纯前端项目无需默认选择后端框架，CLI 项目无需默认选择 UI 框架。
3. **逐项展示候选**：先给出维度概览，让开发者看到可选方向；对当前最重要的维度详细比较。AI 从需求出发自行寻找可行路线和技术，每项标明适用条件、优势、成本、主要约束和有理由的推荐，不把候选压缩成三套固定组合。允许继续展开其他路线和开发者自定义技术；确实只有少数合理方案时说明排除原因，不为凑数量推荐不合适的工具。参考文件中的候选仅用于提醒容易遗漏的方向，既非必选清单，也非候选数量上限。
4. **组合与确认**：根据开发者的逐项选择检查技术、运行环境、数据访问、部署与团队成本是否兼容。把“单体／微服务”与“分层／整洁／六边形”等不同维度分开，不当作互斥项。对冲突给出具体原因和替代组合；关键技术与架构在开发者明确确认前保持待确认状态。
5. **保存决定**：确认后优先更新项目已有等价文档；新项目使用 `.soloweave/context/PROJECT.md` 记录目标、入口、已确认选型和 ADR 链接，用新 ADR 写明问题、候选、理由、组合约束及确认事实。有待定项时明确标记，不伪造批准；有持续开发或阻塞时按 `project-continuity` 保留状态与下一步。纯 Skills 流程不手工生成旧 CLI 的 `approval.json` 或 `checkpoint.json`。

## 推荐依据与候选维护

推荐按需求适配度、开发者经验、维护负担、部署约束、成本、性能、安全与生态成熟度解释，不设脱离上下文的“最佳技术栈”。版本、兼容性、维护状态等可能变化的事实应尽可能核对官方资料；无法核对时标明不确定性，不编造当前版本或支持情况。

参考文件以**判断问题和路线示例**提醒 AI 避免视野过窄：例如 Web 前端可以考虑无框架、客户端渲染与服务端渲染；移动端可以考虑原生与跨平台；数据／AI 只有涉及模型时才比较本地与托管运行。这些是说明如何展开思路的例子，不要求每次列全，不限定可用路线、技术或组合。候选概览应让开发者看见与当前需求有关的不同方向；详细比较只展开重要部分。

`project-setup/SKILL.md` 只保留触发条件、交互顺序和批准边界。新增一份按项目类型和决策维度组织的参考文件，重点提供判断问题、比较标准、典型不兼容点和少量非约束性示例。参考文件不是允许清单、排序表或默认技术栈；AI 可提出未列出的适用技术，开发者提出的技术也必须按同一标准评估。维护参考文件时优先修改判断条件和兼容关系，不把所有组合枚举为固定模板。

## 异常与边界

- 开发者已经指定某项技术：把它作为已给约束核对，不再反复推荐替代品；若与其他要求冲突，指出冲突并等待决定。
- 必要信息缺失：一次只问影响当前关键决策的问题，不用完整问卷阻塞普通项目；可以暂缓不重要的决定。
- 多种项目类型并存：例如移动端加后端 API，分别选维度并检查接口、数据和部署边界，不强制成单仓库或多仓库。
- 现有项目：先识别并沿用实际实现；重构或迁移要由开发者明确提出并确认，不因为参考目录中有别的候选就换栈。
- 候选不在参考文件：正常评估其适用性，不以“未收录”为排除理由。无法在线核对时，明确需要验证的兼容性与维护状态。
- 重大决定未确认：可继续与该决定无关的调查；不得把推荐写成已批准 ADR 或据此实施架构。

## 实施边界与验收

实施时修订根目录 `skills/project-setup/SKILL.md`，新增其按需读取的参考文件，并同步中英文使用与验收说明。保留其他 Skill 名称、SkillHub slug 和现有 Go CLI 资源；当前尚未提交的交接修订一并保留。版本按仓库的 Skill 发布规则递增，具体版本在实施时核对。

以下场景用于真实客户端回归，记录原始提示词、安装版本、Agent 输出及项目文件；静态文字检查不能代替行为验收：

1. **模糊的待办应用**：普通请求未说明项目形态时，AI 不直接假定静态网页并开工；先识别会影响架构的关键缺口。
2. **前后端分离的待办应用**：开发者明确要求后，AI 按适用维度展示前端、后端、数据、架构和交付等候选与推荐，允许交叉组合、自定义和展开更多选项；不能只给三套不可拆分的技术包。
3. **非 Web 项目**：至少以移动端和 CLI／自动化各测试一次，检查选型维度随项目类型变化，不出现强制 Web 前后端选型。
4. **已有项目和指定技术**：Agent 读取实际依赖与 ADR，不擅自换栈；已给约束不反复询问。
5. **确认与兼容性**：故意提出不兼容组合，AI 说明原因；在明确确认前只保存待定状态，确认后再记录 ADR。

验收结果区分“Skill 文件有效且可安装”和“真实 Agent 按预期推荐”。自动选择是否触发由客户端决定，不能凭文档改动宣称通过。
