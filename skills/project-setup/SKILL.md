# 项目设置

## 先了解项目

已有项目先读 README、依赖和锁文件、目录、测试、现有规则及 ADR，以实际实现和有效决定为起点；接入 SoloWeave 不自动换栈。新项目先了解目标用户、核心功能、运行平台、数据和离线需求、交付环境、预算及开发者经验。只追问会改变关键选型的缺口，已给信息不重复问；其他决定可以暂缓。需求模糊到足以影响项目形态时，先澄清或说明不同形态的影响。例如“待办应用”可能是本地页面，也可能需要独立后端，不要直接选定其中一种并开工。

## 按维度讨论选型

先识别适用的项目类型，可包括 Web 前端、后端 API、全栈 Web、移动端、桌面端、CLI／自动化、数据／AI，也可混合或自行扩展。类型只帮助发现需要讨论的维度，不限制 AI 能推荐的技术。列出当前重要维度，再按维度展示可独立选择的候选路线、适用条件、收益、成本和主要约束，给出有理由的建议。主动检查是否遗漏实质不同且可行的路线；有更多合适选项时提供概览并允许展开或自定义，候选少时说明关键排除理由。不要把前端、后端、数据库和架构绑定成少数几套固定组合，也不要为凑数量列出不适用方案。

需要判断维度、兼容性或避免遗漏路线时，按需阅读 [选型判断指南](references/selection-guide.md)。其中的技术和路线只是例子，**不是白名单、默认栈或数量上限**。遇到指南外的类型、技术或组合，按同样的需求和兼容性标准评估，不因未收录而排除。版本、维护状态等易变化事实应尽量核对可信资料；无法核实时标记不确定性。

根据开发者逐项选择，检查运行环境、接口、数据访问、部署和维护成本是否兼容；具体说明冲突与可行替代，不替开发者暗中改选。已给定的选择作为约束核对，不再重复推荐。关键技术和架构在开发者明确确认前保持待确认；与待确认决定无关的调查可以继续。

## 保存已确认决定

确认后优先更新项目已有的等价文档。需要新文件时，用 `.soloweave/context/PROJECT.md` 记录目标、运行入口、主要模块、已确认选型及 ADR 链接；在 `.soloweave/decisions/ADR-NNNN.md` 写明问题、候选、决定、理由、组合约束和开发者确认事实。未确认方案标为“待确认”，不写成已批准 ADR。重大选型变化另建 ADR，指出被替代的决定；持续开发或受阻时按 `project-continuity` 记录状态和下一步，若未安装该 Skill 至少记录当前任务与下一步；不覆盖用户现有内容。

如果项目已有 CLI 管理的 `.soloweave/project.yaml` 与 `approval.json`，先核对其约束及是否被后续 ADR 取代。纯 Skills 流程不手工生成或修改这些机器批准文件，也不伪造 `checkpoint.json`。没有 CLI 仍可完成上述 Markdown 记录。
