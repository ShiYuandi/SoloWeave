# 项目选型判断指南

本指南帮助发现问题、比较方案，不是技术清单或固定推荐。根据实际需求增减类型、维度、技术与组合；开发者提出未列出的技术时，照常评估。只展开会影响当前决定的内容，不把指南当问卷逐项盘问。

## 先找决定依据

确认产品目标、目标用户、核心功能、运行平台、数据来源与敏感性、离线和同步需求、部署与分发、团队经验、维护预算及已确定约束。已有项目先核对实际依赖、运行方式和有效 ADR。某项信息已明确时直接使用；缺失的信息只有在会改变关键推荐时才询问。

按适用维度比较需求适配、学习和维护成本、部署限制、性能、安全、生态成熟度及迁移代价。对当前最重要的维度先给不同可行路线的概览，再给具体候选和理由；检查是否遗漏实质不同的路线，其他维度可暂缓。推荐一个方案时也应保留开发者查看其他可行方向的入口。建议不等于批准。技术版本、平台支持和维护状态可能变化，应尽量核对官方资料；无法核对就说明待验证之处，不编造确定性。

## 按项目形态发现维度

| 形态示例 | 值得判断的维度与兼容性 |
| --- | --- |
| Web 前端 | 页面交互与渲染、路由、浏览器支持、数据来源、部署；可比较无框架、客户端渲染、服务端渲染等路线。纯前端不默认需要后端框架。 |
| 后端 API | 语言和运行时、接口约定、数据一致性、认证、部署与运维；脚本型、编译型等生态只是思考方向，不限语言。 |
| 全栈 Web | 分别考虑前端、服务端、数据及接口边界，再检查构建、部署与团队维护成本；不预先捆成完整技术包。 |
| 移动端 | 目标系统、原生或跨平台、设备能力、离线同步、后端接口、应用分发。移动端与 API 可组合，不预设仓库数量。 |
| 桌面端 | 目标操作系统、系统集成、本地存储、原生或跨平台方案、打包与更新；是否需要远程服务依需求决定。 |
| CLI／自动化 | 运行环境、跨平台与调用方式、配置和凭据、脚本或编译产物分发、调度及失败恢复；不默认需要图形界面。 |
| 数据／AI | 数据来源、处理频率、批量或持续处理、敏感性、质量验证与成本。仅在确实涉及模型时讨论模型类型、本地或托管运行、评估和调用成本。 |

这些形态可混合。遇到游戏、嵌入式或其他项目，先据需求定义适用维度，不强套 Web 表，也不因表中没有该类型而拒绝选型。上表路线均为非约束性示例；可行候选由当前项目决定。

## 组合检查与表达

- 分开讨论应用形态与内部组织方式。例如单体或多服务是部署边界，分层、整洁或六边形是内部依赖组织，不必当作互斥选项。
- 检查选定技术在目标平台、运行时、数据访问、接口、离线、部署与交付上的实际配合；指出确切冲突和替代做法。对未经核实的兼容性保留待验证项。
- 展示可逐项选定的组合：哪些已由开发者指定、哪些是推荐、哪些待定。不要因为开发者选择了表外技术而强行换回示例技术；也不要重复询问已完整给出的选型。
- 决定需要开发者确认时清楚呈现完整组合及理由。确认之前不据此实施重大架构，也不把待定方案写成已批准 ADR。
